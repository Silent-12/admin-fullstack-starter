# Git 提交改动说明生成

根据指定的 git 提交记录，生成结构清晰、面向测试与运维人员可读的中文改动说明文档。

## 触发场景

当用户出现以下任一情况时使用本 skill：
- 提供 commit hash（如 `860e1bb`、完整 SHA）并要求生成说明
- 明确说「基于这次提交写说明」「生成改动说明」「生成测试说明」「输出给测试」
- 要求总结某次提交的新增功能、影响范围、测试关注点
- 用户提及「commit 记录」「提交说明」「改动文档」并指向具体某次提交

## 默认行为

1. **输出路径**：生成的 Markdown 文档默认存放在**当前项目根目录**下，文件名根据改动主题命名（如 `负余额预警与逾期通知改动说明.md`）。
   - 若用户明确指定其他路径，按用户指定路径写入。
   - 若项目根目录无法写入，回退到项目根目录下临时生成，并提示用户手动复制。
2. **不自动提交 git**：仅生成文档文件，不执行 `git add` / `git commit` / `git push`。
3. **不创建多余的配套文件**（如 README、CHANGELOG 等），仅生成一份改动说明文档。

## 执行步骤

### 1. 读取提交元信息与改动

必先执行以下命令，**禁止凭文件名或 commit 标题猜测内容**：

```bash
git show --stat <commit>
git show <commit> -- <file1> <file2> ...
```

- `git show --stat <commit>`：把握改动范围与文件清单。
- `git show <commit> -- <文件分组>`：分批查看实际 diff，避免单次输出过大被截断。
- 若改动文件过多，按模块分组分批读取（如先读 service 层、再读 entity/常量、最后读迁移与配置）。

### 2. 归纳改动主语义

从 diff 中提取：
- **新增功能**：用户可见行为变化、新业务流程、新接口。
- **调整逻辑**：阈值变更、时点变更、状态流转变更。
- **数据库变更**：新增字段、修改字段、回填数据。
- **配置变更**：环境变量、Cron 表达式、模板 CODE。
- **代码模块**：按业务模块归类，不逐文件罗列。

### 3. 生成文档结构

统一采用以下结构输出：

```markdown
# <改动主题>

## 一、新增功能
按功能点分小节，每节包含：业务目的 + 触发条件 + 关键规则。

## 二、影响范围
### 数据库变更
### 配置变更
### 涉及的代码模块（表格：模块 | 文件 | 改动要点）

## 三、测试关注点
编号列表，每条一个可独立验证的测试场景。

## 四、部署清单
按顺序排列的部署步骤。
```

若某节无内容可省略，但不得合并或删除章节标题。

## 命名与术语规范（核心约束）

### 一、禁止裸露专业名词

文档面向测试与运维人员，**禁止**只出现英文字段名、方法名、配置项、数据库列名而不附中文说明。

### 二、统一「中文描述（原文）」格式

所有技术标识（字段名、方法名、配置项、表名、Cron 表达式 key 等）必须采用：

```
中文描述（原文）
```

示例：

| 错误写法 | 正确写法 |
|---|---|
| `negative_balance_check_cron` | 余额不足检查 Cron 表达式（`negative_balance_check_cron`） |
| `negative_balance_notification_mask` | 余额不足通知节点位掩码字段（`negative_balance_notification_mask`） |
| `syncBalanceAlertState` | 同步余额预警状态（`syncBalanceAlertState`） |
| `balance-alert.service.ts` | 余额预警服务（`balance-alert.service.ts`） |
| `ALIYUN_SMS_OVERDUE_TEMPLATE_CODE` | 阿里云短信逾期提醒模板 CODE（`ALIYUN_SMS_OVERDUE_TEMPLATE_CODE`） |
| `createBalanceOverdueRequest` | 创建余额不足自动注销申请（`createBalanceOverdueRequest`） |
| `monthly_service_fee_cron` | 月度服务费 Cron 表达式（`monthly_service_fee_cron`） |

### 三、数据库字段必须标注所属表与类型

涉及数据库字段时，必须说明：
- 所属数据库表（中文名 + 原始表名）
- 字段类型与约束
- 业务含义

示例：

```
用户表（`user`）新增余额不足通知节点位掩码字段（`negative_balance_notification_mask`，微小整数类型，无符号，非空，默认 0）
```

### 四、代码模块表使用中文模块名

涉及代码模块表格时，模块列使用中文业务名，文件列使用「中文服务名 + 原始文件名」：

```markdown
| 模块 | 文件 | 改动要点 |
|---|---|---|
| SIM 卡管理 | 余额预警服务（`balance-alert.service.ts`） | 三阶段预警、四节点短信、位掩码领取/清除 |
| 账户 | 账户服务（`account.service.ts`） | 余额变更时维护位掩码（恢复正数清零） |
```

### 五、技术术语口语化

- `Cron` → 定时任务（首次出现时保留 `Cron` 一词便于对照）
- `Redis NX 锁` → Redis 原子锁（仅在键不存在时写入）
- `位运算` → 保留，但首次出现时前置中文说明
- `幂等` → 保留，首次出现时括注「同一操作只执行一次」

## 写法要求

- 使用祈使语气描述测试点，如「验证」「模拟」「确认」。
- 测试关注点必须**可独立验证**，每条聚焦一个场景。
- 部署清单按**执行顺序**编号，迁移文件顺序不可颠倒时必须显式标注。
- 数据库迁移文件（如 `V017`、`V018`）保留原始编号，不翻译。
- 表格、列表保持 Markdown 格式规范，便于复制到企业 IM 或文档平台。

## 边界情况

### 提交包含多个不相关改动

仍按主目的归纳，用更高层级的概括覆盖，不逐项拼接长句。若实在无法归纳，可拆为「主要改动」与「其他调整」两节。

### 提交仅含文档/配置/测试

省略无关章节，但保留有内容的章节标题。例如纯配置变更可省略「新增功能」，保留「配置变更」「部署清单」。

### 用户要求简化

若用户明确要求「简化」「精简」，按以下顺序压缩：
1. 删除「涉及的代码模块」表格
2. 合并「测试关注点」为 3-5 条核心场景
3. 「新增功能」改为要点列表，不再分小节
4. 保留「数据库变更」「配置变更」「部署清单」完整内容

### 用户指定输出路径

若用户指定路径（如桌面、特定目录），优先写入指定路径。若该路径不在允许写入范围内，回退到项目根目录生成，并提示用户手动复制。

## 禁止事项

- 不读取 `git show` 实际 diff 就凭 commit 标题或文件名生成说明。
- 只描述部分文件改动，忽略其他已提交内容。
- 文档中出现未附中文说明的纯英文专业名词。
- 自动执行 `git add` / `git commit` / `git push`。
- 创建改动说明文档之外的任何配套文件。
